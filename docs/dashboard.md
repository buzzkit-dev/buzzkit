# Dashboard

How `apps/web` (React Router 8 SSR on Cloudflare Workers) is built, authenticates against the API, and what it ships in which phase. The dashboard consumes the same public API as everyone else; there are no private endpoints (the framework test from [overview.md](overview.md)). Everything visual follows [design.md](design.md).

## Packages

| Package | Role |
|---|---|
| `@buzzkit/ui` (`packages/ui`) | The design system, ported 1:1 from feedbase: shadcn (Base UI style) + Tailwind v4 tokens, Open Runde, Central Icons pipeline (`generate:icons` scans the repo for `name='Icon…'` literals). Chat-specific pieces were left behind; everything else is identical |
| `@buzzkit/eden` (`packages/eden`) | Eden Treaty over `@buzzkit/api/contract` (`apps/api/src/modules/contract.ts`: the v1 router without runtime adapters). Unwraps the `{ success, data, error, metadata }` envelope so callers get `data` or a normalized `{ status, value: { code, message, param } }` error. Types are inferred from the API's emitted declarations (`bun run types:emit` in `apps/api` → `.types/`, git-ignored; turbo runs it before `dev` / `build` / `check-types`) |
| `@buzzkit/web` (`apps/web`) | The dashboard. `app/lib/api.server.ts` wraps the Eden client per call (bearer token + `buzzkit-workspace` / `buzzkit-tenant` headers), maps 401 to a sign-out, and derives every entity type (`Workspace`, `Credential`, `Tenant`, …) from calls, never by hand |

## The server-side proxy pattern

The API authenticates `/v1/*` with `Authorization: Bearer <token>` only ([authentication.md](authentication.md)), and BetterAuth is mounted on the API at `/v1/auth` (`authHandler`). The dashboard adds nothing in between:

1. The browser signs in **directly against the API** with the BetterAuth client (`lib/auth.client.ts`, `baseURL: API_URL`, `basePath: '/v1/auth'`): `signIn.email`, `signUp.email`, `signIn.social({ provider: 'github' })`. The API answers with its own httpOnly session cookie (`buzzkit.session_token`, `__Secure-` prefixed in production). CORS on the API allows `DASHBOARD_URL` with credentials.
2. That cookie reaches the dashboard because dashboard and API are **same-site**: on localhost, cookies ignore the port; deployed, both live under one parent domain and the API sets the cookie on it (BetterAuth's `crossSubDomainCookies`, the domain derived from `BETTER_AUTH_URL` and `DASHBOARD_URL` by `@buzzkit/auth/cookies`, nothing to configure). That also puts the cookie on the root domain, so a landing page there can tell a signed-in visitor from a new one. A self-hoster puts API and dashboard under one domain for the same reason.
3. Route **loaders** read the cookie (`lib/session.server.ts`: `requireSession`, `readSessionToken`) and forward its value, BetterAuth's signed session token, as the bearer header on server-side `/v1/*` calls via `lib/api.server.ts`. The Worker validates nothing itself: the API verifies the token on every call, and a forged or expired cookie is a 401 that expires it. Where the Worker does need BetterAuth's answer it uses BetterAuth's client server-side with the cookie forwarded: `requireAnonymous` on the auth pages asks `getSession`, `signOut` goes through `signOut`. The browser never sees the token: the cookie is httpOnly and nothing is stored client-side.
4. Signing out is an intent (`sign-out`) on the action of whichever route shows the control (the workspace layout for the account menu, the invite page for its "Sign out"): `signOut` in `lib/session.server.ts` calls `/v1/auth/sign-out` with the bearer token and forwards BetterAuth's own `Set-Cookie` headers to the browser, so BetterAuth decides how its cookie is expired. Only an API 401 (a session BetterAuth no longer knows, so sign-out cannot clear it) falls back to `signedOutRedirect`, which expires the cookie by the names and domain `@buzzkit/auth/cookies` exports.

`BETTER_AUTH_URL` is the API origin plus `/v1/auth` (BetterAuth routes by that path, so `authHandler` re-adds it to the request Elysia's `mount` stripped), and GitHub's callback URL is `<BETTER_AUTH_URL>/callback/github`, i.e. `http://localhost:8790/v1/auth/callback/github` locally. The dashboard shows the GitHub button when it has the OAuth app's public `GITHUB_CLIENT_ID`; the API holds the id and the secret and runs the flow.

`/login` and `/signup` share one pathless layout (`routes/(auth)/layout.tsx`, a pathless group in Next.js' bracket notation) that renders **one persistent form** (`components/auth/form.tsx`, `AuthForm`): the routes only contribute `handle.auth` (mode, title, description, footer link) and loader data (`apiUrl`, providers, redirect, error), and render nothing themselves. Switching between the two keeps Email, Password and the submit button exactly where they are; the Name field is the only thing that moves, rising out from behind Email (its grid row unfolding from `0fr` to `1fr` while the field inside keeps its natural height, translate up from 24px, scale from 0.92, fade in, 0.4s bounce-0 spring) and folding back the same way; the "Must be at least 8 characters" hint under Password does the mirror image, unfolding downward from behind the input. The fields below Name sit on their own `bg-card` layer so Name really comes from behind them. `/invite/:token` renders its own static card; workspace creation (`/onboarding`) uses the onboarding layout.

Field-level problems (a bad email, a short or breached password) show under the field; anything that is not about one field (wrong credentials, the API unreachable, a GitHub round trip that failed) is a `toast.error`, never an inline banner. Toasts are always top-centered.

Passwords must be at least 8 characters (`minPasswordLength`) and are checked against Have I Been Pwned's breached-password corpus on sign-up (BetterAuth's `haveIBeenPwned` plugin, k-anonymity: only a hash prefix leaves the server); a compromised password comes back as `PASSWORD_COMPROMISED` and the form says so under the field.

The only cookie the dashboard writes itself is `buzzkit.workspace`, the last visited workspace slug, unsigned because it is not security-relevant. Only `/`-relative `redirect` values are honored (`safeRedirect`).

There are no action-only routes: a mutation belongs to the action of the route that renders its control, selected by an `intent` field (the workspace layout handles `profile`, `sign-out` and `create-workspace`; the invite page handles `sign-out`). Every action body lives under **`lib/actions/`** (`onboarding`, `workspace` (profile, sign-out, create-workspace, settings incl. delete, and the shared form-to-workspace mapping), `invite`, `connect`, `channels`, `members`, `tenants`, `keys`, `topics`, `subscribers`, `messages`; `context.server.ts` has `beginAction`, the env/token/form preamble they all share); a route file only does `export const action = workspaceAction`. `lib/api.server.ts` is the typed API client those actions and the loaders call.

Two rules fall out of `api.server.ts`:

- **Any API 401 expires the cookie and redirects to `/login`.** Loaders and actions never handle expired sessions themselves.
- Envelope failures throw `ApiError(status, code, message, param, details)`; actions map codes to field messages (`conflict` on `POST /workspaces` → "This slug is already taken"). `param` lets the onboarding guide attach a provider rejection to the field that caused it.
- `unwrap` JSON-round-trips every payload: Treaty revives ISO strings into `Date`s at runtime but the derived types say `string`; the round-trip makes the runtime shape match so loader data serializes predictably.

### Tenant selection

Every data-plane call carries `buzzkit-tenant`. The workspace layout resolves **which tenant** once per request (`resolveTenant` in `lib/session.server.ts`: `?tenant=<slug>` on any route wins, then the `buzzkit.tenants` cookie, a per-workspace map of the last choice, then `default`), validates it against `GET /v1/tenants`, falls back to the default tenant for an unknown slug, writes the cookie when the choice changed, and hands the `Tenant` down through the outlet context; every data loader and action reads the same resolver (`beginAction` returns `tenant`), so nothing hardcodes `default` any more except the first-run onboarding, which is default-only by design. The `?tenant=` form is the shareable one: a colleague opening it lands on that tenant and stays there.

**Tenants are not projects.** A workspace with one tenant never shows any of this: no switcher section, no suffix, no banner; the simple-app case never learns tenants exist, exactly like the API. With more than one tenant, the workspace switcher's trigger reads `Repro · Acme Corp` (tenant in `fg-2`, only while a non-default tenant is selected; on the default tenant the trigger is just the workspace name) and its menu gains a **Tenants** group below the workspaces (building glyph, check on the active one, "Manage tenants" into Settings → Tenants); picking one navigates to the current path with `?tenant=`. Viewing anything but the default tenant is deliberately not seamless: on the tenant-scoped pages (Overview, Workflows, Subscribers, Segments, Topics, Messages, Events, Settings → Channels; never on workspace-level pages such as API keys, General, Members, Tenants or the Audit log) an amber strip sits above the content panel, on the subtle background, the same 32px row at the same 12px top as the workspace switcher ("Viewing tenant Acme Corp. Its subscribers, topics, messages and credentials are isolated from every other tenant." with a "Back to default" action), because a tenant view is for inspecting or debugging one customer's data, not a second home. The onboarding redirect applies to the default tenant only: a fresh non-default tenant shows the Overview with its setup checklist and Settings → Channels with Connect buttons. Workspace-level pages (General, Members, API keys, Events) do not change with the tenant.

## Layout: sidebar + content card

**Connected channels are decided once.** The workspace layout loader already lists the tenant's credentials (to send a fresh workspace to onboarding); it derives `connected` from them with `lib/channels.ts` (`connectedChannels`, catalog order) and hands it down through the outlet context. Every channel picker, filter and column reads that list: the Messages channel filter (hidden when only one channel is connected), the send dialog's Channel select, the topics dialog's channel rows and the topics table's per-channel columns. No page lists credentials for itself, and nothing in the dashboard offers push to a workspace that never connected a push provider.

Every signed-in page lives in `routes/[slug]/layout.tsx`: the page background is `background-subtle`, a **240px sidebar** on the left, and the route's content inside a raised `bg-card` panel (`rounded-2xl`, `shadow-sm`, 8px gutter, `px-8.5 py-7.5`) that scrolls on its own. The panel is a **flex column** (`flex flex-col overflow-y-auto`): as a row it would stretch the route to its own height and the overflow would never become scrollable. The page itself never scrolls, vertically or horizontally: tall pages scroll inside the panel, and wide content (tables) scrolls inside its own `overflow-x-auto` container. There is no top bar; the pill tabs from feedbase are gone. Pages fill the panel: no `mx-auto`, no max width. Each page opens with a header row, `justify-between items-center`: title (`text-2xl`) and one-line description top-left, the page's actions top-right and vertically centered on the title block; detail pages put the avatar or tile beside the title and their destructive action in that same top-right slot. Page descriptions say what the page is for and stop: "Manage workspace API keys.", "Manage notification topics." No explanations, no reassurance, no feature copy.

The sidebar (`components/layout/sidebar.tsx`) is data-driven from `components/layout/navigation.ts`, the single source of the information architecture:

- **Top**: the workspace switcher as a full-width row. **Bottom**: the account menu as a full-width row (avatar, name, grabber chevron). Between them the nav scrolls.
- **Sections** with quiet `text-xs fg-2` labels: Overview (unlabelled) · **Messaging** (Messages with their deliveries, Workflows expandable into Catalog and Runs, Events expandable into Catalog and Stream: what the tenant sends and reacts to, first) · **Audience** (Subscribers, Segments, Topics) · **Developers** (API keys, Webhooks, Sources) · **Workspace** (Settings, expandable: General, Channels, Tenants, Workflows, Members, Audit log, Billing `Soon`). Channels (the provider connections) are configuration and live under Settings, not in the main nav; a broadcast is a message to a segment sent from the Messages page and templates belong inside workflows, so neither gets a tab; no section ever holds a single item (Engage held only Workflows once Campaigns went; Messages and Events joined it as Messaging); deliveries are reached through a message, not a tab of their own.
- **Every row is a ghost button in disguise**: items, the workspace switcher and the account row share the ghost `Button`'s metrics (`h-8`, `rounded-xl`, `px-2.5`, superellipse corners; avatar rows keep `pl-1.25` so their text lines up with item labels) and its hover surface (`bg-a2/70`, press scale 0.985, gentler than a button because the row is wide). Sub-items use the `sm` size (`h-7.5`, `rounded-[10px]`). **One sliding highlight** (`useAnimatedIndicator`) across the whole nav, sub-items included; it rests on the active page and follows the pointer, exactly like menus and the onboarding rows. Icons are 18px and lift to 85% under the highlight or when active.
- **Expandable items** (`children`) are buttons with a rotating chevron, never a destination: the highlight visits them only under the pointer (to open or close), the resting highlight always sits on the active sub-item. Their sub-items unfold and fold (height + opacity, 0.3s bounce-0 spring opening, 0.2s closing, `AnimatePresence` so closing animates too) behind a left rail, and the chevron rotates in 150ms and open automatically when one of them is the current page. `Soon` items render dimmed with a badge and do not link.
- **Every page in the sidebar resolves.** Pages that are not built yet fall through to `routes/[slug]/planned/index.tsx` (the `*` child of `/:slug`), which looks the path up in `navigation.ts` and renders an `EmptyState` naming the phase (`planned`). A path that is not in the navigation, or is marked `soon`, is a 404. When a real page ships, its route is added above the catch-all and the `planned` field is removed.

The settings pages no longer carry their own sub-navigation: Settings' sub-items are the sidebar's.

## Onboarding

**Onboarding is mandatory.** A workspace with no credential (no connected provider) has nothing to show, so `routes/[slug]/layout.tsx` redirects every page under `/:slug` to `/:slug/onboarding` until the first credential exists; there is no separate "completed" flag to keep in sync, the connection is the completion. It is **first setup only**: once the workspace has a credential, `/:slug/onboarding` (any path under it) redirects to `/:slug`, exactly like `/onboarding` redirects an account that already has a workspace; further channels and providers are managed in Settings → Channels. The route skips revalidation after a successful connect (`shouldRevalidate`) so the Connected screen stays on screen after the credential exists. The product promise is "sign up, upload your provider key, send". The onboarding is one **centered card** (the `Card` anatomy: header, content, footer strip) with four thin progress lines above it (`Workspace → Channel → Provider → Connect`). Nothing else on the page, exactly like `/new`: no header, no skip link; the flow is not skippable from inside (the dashboard stays reachable by URL).

- **Progress** (`components/onboarding/progress.tsx`): four `h-1` tracks in `bg-3` with a `fg-4` fill that animates its width on a 0.5s bounce-0 spring. Done steps are full, the current step carries a small fill that grows with sub-progress (the Connect line fills as the guide advances), upcoming steps are empty. No numbers, no labels, no icons; the element is a `progressbar` with `aria-valuetext` for screen readers.
- **Workspace** (`/onboarding`): name + slug, shown in the onboarding card with the progress lines (step 1 of 4). The default tenant is created automatically; the user never sees it.
- **Channel** (`/:slug/onboarding`, "Connect a channel"): `ChoiceRow`s (icon tile, name, one-line description, chevron) for every channel from `catalog.ts`: Push notifications and Email are available; SMS and Web push render dimmed with a `Soon` badge. Channel rows never show `Connected` (the badge belongs to the provider rows, where the connection actually is); a channel with a credential simply stays clickable. Rows share one sliding highlight (`useAnimatedIndicator`, the same mechanic as menus and the settings nav): a `bg-a2` pill glides to the hovered row, fades out when the pointer leaves, and scales to `0.9925` on press; the `IconTile` brings its own `bg-4/70` hairline ring; rows draw no background of their own, never move, and cast no shadow.
- **Provider** (`/:slug/onboarding/:channel`, "Choose a push provider"): the same rows per provider, platform as small badges (Apple `iOS`, Firebase Cloud Messaging `Android`; Resend, with Postmark and SendGrid listed as `Soon`). Every channel shows this step, even with one live provider, so the choice is explicit. Footer: `Back`.
- **Connect** (`/:slug/onboarding/:channel/:provider`): the provider guide, **one sub-step at a time**.
- **The card has three slots** (`OnboardingLayout`): a header whose text switches instantly while its height eases on the same 400ms curve (a `SizeAnimator` around it, so a description that wraps to one more line never snaps the card), a content area wrapped in `StepTransition` (`components/onboarding/transition.tsx`), and a footer anchored below it. Every view of the funnel (channels, providers, each guide sub-step, the connected state) produces `{ title, description, content, footer }` (`OnboardingSlots`); the route component picks the slots for the current URL and guide state and hands them to the shell. The transition is keyed by view + sub-step and its direction comes from a numeric position (`channels 0 < providers 100 < guide 200+n < connected 900`), stored in state the moment the key changes, so Back always slides back. Because the footer lives outside the animated region, it simply rides the card's height animation (`SizeAnimator`, 400ms to match the spring) instead of jumping. The guide's state lives in `useProviderGuide`, keyed by provider; its Next button submits the content's form by `form` id since they sit in different slots. The Apple guide follows the real 2026 portal flow: Keys → Register a New Key (tick APNs, Configure) → Configure Key (Environment `Sandbox & Production`, Key Restriction `Team Scoped`, which Apple locks after saving) → Register and Download → Key ID from View Key Details → Team ID from the portal header (`Team name - TEAMID`, top right) → bundle ID from Identifiers.

### The provider guide

The guide is the heart of the onboarding. Inside the card: the sub-step's title and one-line description as the card header (there is no static guide title; the step is the header, and it switches instantly while the content below animates), the illustration (a `bg-2` panel whose inner box keeps the mock's own `16/10` ratio, so the padding reads the same on every side), an optional outbound link (`Open Keys`, `Open the Firebase console`, …), and the field(s) this sub-step produces. The footer carries `Back`, `n of N`, and `Next` (enabled once the sub-step's fields are valid; Enter in a field does the same) or, on the last sub-step, the connect action. Sub-steps swap with a 0.4s bounce-0 spring, directional (`AnimatePresence mode='popLayout'` so the entering step starts while the leaving one is still on its way out): the leaving step slides a full width away, scales to 0.85 and blurs to 2px (no fade, so it has to leave completely); the entering one comes from a full width on the other side, scaling up from 0.85 while its 4px blur resolves to zero. Row pages (channels, providers) never scale: whatever is on the other side, a row page enters and leaves with the slide and a 1 to 1.5px blur only. The 0.85 scale and heavier blur belong to preview pages (guide steps, connected) in both directions, so going back from a guide to the provider list means the guide scales out while the list slides in flat. The card edge clips the slide horizontally and the animator's own box clips vertically via a `clip-path` inset that is open on the sides, so a step that shrinks the card never spills under the footer inside a `SizeAnimator` that bleeds past the card padding so shadows and the slide never clip; the centered `n of N` counter rolls with NumberFlow on the same 400ms curve and the primary label swaps from `Next` to the connect label with `TextSwap` (NumberFlow-style vertical roll with masked edges, the button width springs to fit).

- Each guide (`components/onboarding/guides/apns.tsx`, `fcm.tsx`, `resend.tsx`) is an ordered list of sub-steps: title, description, link, note, **fields**, illustration. Fields sit inside the step that produces them: the `.p8` drop zone under "Download the .p8 file", the Key ID input under "Copy the Key ID", the service-account JSON drop under "Upload the JSON file". There is no environment picker: the API detects it from the key. While a file-field sub-step is showing, **the whole page is the drop target**: dragging a file anywhere raises a full-screen overlay (portal, blurred backdrop, dashed panel) that already judges the type mid-drag from the MIME info the browser exposes (unknown types pass, clearly wrong ones turn the panel red and say what is expected); on drop the file name and type are checked against the field's `accept` list, a wrong file is rejected inline under the drop zone without being read, and a right one is read in the browser (`file.text()`) and submitted as a hidden field; the APNs `.p8` is checked for a PKCS #8 header and the Firebase JSON for `project_id` / `client_email` / `private_key` before anything is sent.
- **A refresh keeps your place.** The sub-step lives in the URL (`?step=n`, written with a replace navigation that `shouldRevalidate` exempts from re-running the loader, so even the server render lands on the right step) and the non-secret answers (Key ID, Team ID, bundle ID, which fields were touched) live in `sessionStorage` per workspace and provider, cleared on success. **Secrets are never stored in the browser**: the `.p8`, the service-account JSON and the Resend key have to be dropped or pasted again after a reload, and the guide steps back to that field if a later step was open.
- **The connect form always carries every field of the guide**, including fields on sub-steps that were skipped because their value was derived (the Key ID read from `AuthKey_<ID>.p8`); only the visible steps decide what the user sees, never what gets sent. When the API points an error at a field on a skipped sub-step, that sub-step is un-skipped and shown with the error; an error that points at no field at all is shown under the last sub-step, so a rejection is never silent. The primary button never changes its `type`: it is always a plain button that calls `requestSubmit()` on the last sub-step (a button that flips to `type='submit'` inside the click that reaches the last step would be submitted by the browser's default action on that very click). The derived map is persisted alongside the public values, so the step list and `?step` numbering survive a reload.
- **Validation waits for you to finish.** A field's error appears when you leave it or press Enter, never while you type; editing a field that already shows an error hides the error again until the next blur or Enter. Enter on a valid field is the same as Next.
- **Fields that can be derived are.** A file field may `derive` other values from the file (the APNs `.p8` is named `AuthKey_<KEYID>.p8`, so dropping it fills the Key ID), and a step marked `skipWhenDerived` drops out of the sequence while every field it owns came from a derivation, so the Key ID step only appears when Apple's file name doesn't carry it. Example ids in placeholders and illustrations are invented but shaped like the real thing (ten uppercase alphanumerics).
- **Connect** posts one form (every field travels as a hidden input, so earlier sub-steps stay part of the submission) to the route action, which builds the `CredentialUpload` (`guides/upload.ts`) and calls `POST /v1/credentials` on the default tenant. The API validates with a real provider call and, for APNs, probes Sandbox and Production itself (one `.p8` covers both when the key was configured for both, so the guide asks for no environment) and answers with one credential per accepted environment. All `active` renders the connected state (environments listed), `unvalidated` (provider unreachable, which is what local `wrangler dev` on macOS produces for APNs) renders an amber "saved, not verified" state with `Validate again` (`POST /v1/credentials/:id/validate` for each), and a provider rejection (400) surfaces inline; when the API names a `param` the guide jumps back to the sub-step that owns that field.
- **Connected state**: same card, header with the provider glyph, a row list (status badge, environment, Team ID / Key ID / bundle ID, or project + service account), footer with `Add another channel` (only while other channels are unconnected) and `Go to the dashboard`.

Illustrations are composed from `components/onboarding/illustration/` primitives (`Browser`, `Sidebar`, `Page`, `PageTitle`, `MockButton`, `MockInput`, `MockCheckbox`, `MockRow`, `MockTabs`, `MockDialog`, `Spot`, `Callout`) and follow the structure and copy of the real Apple Developer, Firebase and Resend screens; the single sky `Spot` ring marks what to click or copy. They are tokens-only so they read as part of the product, sized for the card (the mock sidebar hides under `sm`), and meant to be tightened against real screenshots of those dashboards.

## Subscribers

The first data page, and the pattern every list + detail page follows.

- **List** (`routes/[slug]/subscribers/index.tsx`): page header with the lookup field in the top-right slot: no button, it navigates to `?q=` 300ms after the last keystroke with the field's `loading` spinner on until the page has loaded, and clearing it returns to the list (the API has no search, and subscribers are addressed by *your* id, so lookup is an exact `GET /v1/subscribers/:externalId` and either shows that one row or says it does not exist), then a paged `Table` (the shared stack: `readPage` / `paginate` / `TablePagination`, 50 per page): **Subscriber** (avatar initials, `name` or `externalId` with a `Verified` badge, the id or email underneath, the whole cell links to the detail), **Country** (flag from `public/flags` + `Intl.DisplayNames` name, from the system attribute `$country`, `Unknown` when the device never identified), **Channels** (one badge per way to reach them, from the list's `channels` and `platforms`: `iOS` blue, `Android` purple, `Email` amber, `None`; green stays reserved for `Verified`), **Subscribed** (`Time`), **Last seen** (`TimeAgo` over the list's `lastSeenAt`, `Never`). System attributes (`$country`, `$city`, `$region`, `$timezone`, `$language`) are stamped by the API on device requests, never by the dashboard. A tenant with no subscribers gets an `EmptyState` inside the same card as the table (the one empty-state pattern every list page follows: Messages, Topics, Events, API keys, Subscribers) whose identify `curl` carries the *selected tenant's* live client key (`bk_pk_…`, auto-created with every workspace and tenant, public and therefore readable from the key list), falling back to a workspace-key placeholder for a tenant whose client key was revoked. Messages cannot do the same: `POST /v1/messages` needs a secret workspace or tenant key, which the API shows once and never again, so that snippet keeps a placeholder. The page shows the selected tenant's providers.
- **Detail** (`routes/[slug]/subscribers/[externalId]/index.tsx`): a profile. No page header (the list already showed the name and id) and no delete: a subscriber is not something you remove, you remove their subscriptions. Two columns (`minmax(0,1fr) 22rem`) inside their own scroller under the pinned back link: the left column scrolls, the right column is sticky at the top and, when taller than the viewport, scrolls on its own (`max-h-[calc(100dvh-8rem)]`, cards `shrink-0`); the page and the content panel never scroll here. Left: **Overview**, a definition-list card (Name, External id with the `Verified` badge, Email, Country with flag, City, Timezone with the local time, Language, Subscribed, Last seen, Verified); every textual value is a click-to-copy button with the press pattern, a clipboard glyph that appears on hover and swaps to a green check for 1.5s after copying (the code block's icon swap, no toast); then **Messages**, a `Table` of the latest deliveries addressed to this person (`GET /v1/subscribers/:id/deliveries`: title and body, channel, `DeliveryStatusBadge`, sent time); then **Activity**, the person's event stream (`GET /v1/subscribers/:id/timeline`, newest first) as rows with a tile, a plain-language label from `components/events/stream.ts` ("iOS device registered", "Preferences changed", or the custom name itself), where it came from ("from iOS", "from System"), and when it happened. Right: **Subscriptions** (mute / remove per device), **Preferences** (one compact row per topic: name and description, then a `ChannelBadge` for every channel the person currently receives it on, or quiet "Opted out"; editing lives behind a `…` menu of checkbox items, one per channel the topic offers, so a fifth channel adds a menu line, not another switch), **Attributes** (the customer's own keys only; name, email and system keys live in the profile card). Every empty section is a small `EmptyState`.
- All mutations are intents on the detail route's action (`lib/actions/subscribers.server.ts`: `subscription-enabled`, `subscription-remove`, `preference`, `delete`), fired through `useActionFetcher` so failures toast and React Router revalidates the page.
- The sidebar marks a section active for its nested pages too (`/subscribers/:externalId` keeps Subscribers lit); only Overview and sub-items (General, Members, …) match their path exactly, since sub-items share a prefix.

A Recipients / Topic card and a Timing card were tried and dropped: the delivery rows already link to every subscriber, and the two cards are enough for now.

The subscriber profile's Activity feed renders through the same module, so an event reads identically on the profile, in the tail and on its page.

## Paged tables

Three layers, so a route never computes page numbers or links:

1. **API page** — every list is `{ items, hasMore, nextCursor, total? }` (`docs/api/conventions.md`).
2. **`lib/utils/pagination.ts`** — `readPage(request)` reads `?cursor=` and returns the `{ limit, cursor }` query for the API; `paginate(request, page)` returns `{ items, pagination }` where `pagination` is `{ page, pageCount, previous, next }`: the page number counted from the cursor trail in the URL, the page count and total from `total`, and Previous / Next as hrefs that keep every other query param. Previous exists without backward paging in the API because the visited cursors ride along in `?trail=`.
3. **`TablePagination` from `@buzzkit/ui`** — `<TablePagination {...pagination} />`, composed as the last child of `Table` like `TableHeader` and `TableBody`; `Table` lifts it out of the scroll viewport so it never scrolls, in either direction. It navigates through the design system's `LinkProvider`, which `root.tsx` hands react-router's `Link` once for the whole app (`<LinkProvider link={Link}>`). The row disables Previous on the first page and Next on the last (or when there is no next cursor), reads "Page 2 / 3 (131)" with rolling numbers, and renders nothing for a single page.

A paged route is therefore: `const page = await listX(ctx, token, slug, readPage(request)); return paginate(request, page);` in the loader, and `<Card><Table><TableHeader>…</TableHeader><TableBody>…</TableBody><TablePagination {...pagination} /></Table></Card>` in the view.
