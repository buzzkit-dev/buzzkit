# Data Model

PostgreSQL schema, owned by `packages/database` (Drizzle). Tables land per roadmap phase; this file is updated in the same change as every schema migration.

## Conventions (all tables, no exceptions)

- **Soft delete only.** Every mutable table has `deletedAt`; deletes are `update … set deletedAt`, reads filter `isNull(deletedAt)`, unique constraints are partial (`where deleted_at is null`). Exceptions, all deliberate: append-only ledgers (`event`, `delivery_attempt`), `subscriber_preference` (hard rows resolved against live topics), `delivery` (follows its message; mutated by the state machine, never deleted), and BetterAuth's `session`/`account`/`verification`.
- **Identity PKs internally; Sqids-prefixed strings externally** (`ws_…`, `tnt_…`; subscribers get 32-char sqids). Numeric IDs never appear in API responses. Every table we own uses a **`bigint` identity** (`bigId()` / `bigRef()` in `schema/shared.ts`) — int32 would be exhausted in days on the ledgers at the target rate, and one id type everywhere keeps FKs uniform; Sqids encodes up to 2^53 without changing the id shape. BetterAuth's tables keep their own text ids.
- **`timestamptz` everywhere** (`createdAt` / `updatedAt` / every `*At`), via the shared column helpers in `schema/shared.ts`. DB-side `now()` defaults are absolute instants regardless of the origin's time zone — with Hyperdrive's transaction-mode pooling the session time zone cannot be relied on, so `timestamp without time zone` would have skewed every sweep that compares DB and Worker clocks. Raw SQL casts use `::timestamptz`.
- **Shared enums.** `channel` and `provider` live in `schema/shared.ts` and are reused by every table that carries them (no `text` duplicates of an enum); every status/kind discriminator is a `pgEnum` (incl. `api_key_kind`).
- **DB-enforced invariants.** `jsonb_typeof(...) = 'object'` CHECKs on every object-shaped JSONB column (`tenant.settings/metadata`, `subscriber.attributes`, `topic.channel_defaults`, `credential.details`, `message.targets/payload`); `api_key` kind↔tenant consistency; push subscriptions must carry a platform.
- **FK delete policy.** Control-plane FKs cascade (only ever reached by operator SQL — the app never hard-deletes); ledger FKs (`tenant`/`message`/`subscriber`/`subscription` → `delivery`, `delivery` → `delivery_attempt`, `tenant` → `message`) are `restrict` so a purge must be explicit; audit pointers (`created_by_user_id`, `invited_by_member_id`, `accepted_member_id`) are `set null`.
- **Index naming.** `<table>_<columns>_unique` / `<table>_<columns>_idx`, or a purpose name for partial/expression indexes (`*_fanout_idx`, `*_due_idx`, `*_unsettled_idx`, `*_stale_idx`, `*_processing_idx`, `*_expiry_idx`, `*_unfinalized_idx`, `*_created_brin`). Every keyset list has a `(scope, id)` index; every sweep has a partial index whose predicate matches the query exactly; no index exists without a query that uses it.
- **Tenant scoping.** Every data-plane table carries `tenantId`; every query must filter by it. Control-plane tables (workspace, member, invite, api_key) carry `workspaceId`.

## Tables

### Phase 1 — identity & tenancy *(implemented — migration `0000`)*

- `user`, `session`, `account`, `verification` — BetterAuth (1.6.25; pinned, its schema expectations change between minors). `user` ids are BetterAuth text ids, not serials.
- `workspace` — slug partial-unique. `workspace_member` — role enum (member/admin/owner), one active membership per (workspace, user).
- `tenant` — the isolation boundary. Slug partial-unique **per workspace**; exactly one `is_default = true` per workspace (partial unique index), created in the workspace-create transaction; `metadata` JSONB for platform customer ids.
- `api_key` — kind `workspace` | `tenant` (tenant keys carry `tenant_id`), SHA-256 `key_hash` (unique), display `prefix`/`last4`, `scopes` text[], `expires_at`/`revoked_at`/`last_used_at`.
- `workspace_invite` — token partial-unique, one pending invite per (workspace, email), 7-day expiry, accepted → `accepted_member_id`.

### Phase 2 — credentials & events *(implemented)*

- `credential` — tenant-scoped; envelope-encrypted secret (`secret_ciphertext`/`secret_iv` sealed by a per-credential DEK, `dek_ciphertext`/`dek_iv` sealed by the master key, `key_version` for rotation); non-secret `details` JSONB (APNs: teamId/keyId/bundleId; FCM: projectId/clientEmail); enums channel (push — email/sms later), provider (apns|fcm), environment (production|sandbox), status (unvalidated|active|invalid); one live row per (tenant, channel, provider, environment) via partial unique index.
- `event` — the append-only **audit ledger** (the control-plane audit log, and the control-plane source of webhooks): workspace/tenant scope, actor columns (type/member/key/display), Stripe-style names, target type + bare sqid id, `data` JSONB, request metadata. No soft delete — rows are never deleted. Since engine phase E1 it carries control-plane facts only; subscriber lifecycle lives on the event stream (below).

### Phase 3 — subscribers, subscriptions, topics *(implemented)*

- `subscriber` — tenant-scoped, (tenant, external_id) partial-unique, `attributes` JSONB (tag data / segment fuel), `identity_verified_at` (client HMAC proof).
- `subscription` — one way to reach a subscriber on one channel: `channel` enum + `endpoint` (push token / email address / later phone), `platform` (push only), **`enabled`** (per-subscription mute — the work-iPhone case), status enum (active|invalid) + invalidation fields for the delivery feedback loop. (tenant, channel, endpoint) partial-unique so re-registration is idempotent and endpoints move between subscribers.
- `topic` — tenant-scoped notification categories, (tenant, slug) partial-unique, `channels` (`channel[]`, non-empty: the channels the topic is offered on; migration `0001`), `default_opted_in` baseline + `channel_defaults` JSONB per-channel overrides.
- `subscriber_preference` — (subscriber, topic, channel) unique — preferences are per topic × channel; stores only deviations from the topic's channel default; hard rows (no soft delete — resolved against live topics).
- Send-time resolution (Phase 4): a topic send on a channel reaches the subscriptions that are `enabled` AND `active` AND whose (topic, channel) preference resolves opted-in.

> Migrations were **squashed to a single `0000`** pre-launch when the subscription model landed — nothing was deployed anywhere yet.
- `tenant` carries `identity_secret` (client HMAC verification) and **`settings` JSONB** — Stripe-style structured groups (identity, channels), resolved with defaults at read time, deep-merged on PATCH, validated against a settings catalog; `api_key` has kind `client` + plaintext `token` column (client keys are public and re-viewable).

### Phase 4 — sending *(implemented)*

- `message` — tenant-scoped send request: channel, `topic` (slug snapshot) + `topic_id` (FK, `restrict`; fan-out resolves by id so a rename between create and fan-out cannot retarget), `targets` JSONB (`{ to?, topic? }`), `payload` JSONB, `idempotency_key` (partial-unique per tenant), `expires_at` (ttl, NOT NULL), status enum (queued → processing → completed), counters `total`/`sent`/`delivered`/`bounced`/`failed`/`invalid` — a **projection of `delivery`**: incremented per batch while processing, recounted exactly from the deliveries at completion (completion itself is derived from "no unsettled delivery", never from counter arithmetic), healed by the cron; funnel semantics `total ≥ sent ≥ delivered`, `sent + failed + invalid = total` when complete, `fanout_cursor` (resumable self-chaining fan-out), `fanout_completed_at` (completion requires fan-out to have finished), `completed_at`.
- `delivery` — one per (message, subscription) (unique): tenant, subscriber, subscription, channel, `provider` (shared enum), status enum (pending | retrying | sent | delivered | bounced | failed | invalid), `attempts`, `last_error_code` (shared taxonomy) + `last_error_message` (provider reason), `provider_message_id`, `next_attempt_at` (durable retry schedule; partial index for the reconciliation sweep), expression index `coalesce(lease_expires_at, created_at)` for the stale sweep, BRIN on `created_at` for retention cut-offs, `lease_expires_at` (per-attempt claim — set atomically before the provider call, cleared on settle; an expired lease with no `next_attempt_at` marks a worker that died mid-attempt), `first/last_attempted_at`, `sent_at`, `settled_at`. `(message_id, status, id)` serves the "anything unsettled?" probe, status-filtered listing, and the completion recount; `delivery_due_idx` is partial on `status = 'retrying' and next_attempt_at is not null` so freshly fanned-out rows never enter it. Attempt insert + delivery update + subscription invalidation commit in one short transaction.
- `delivery_attempt` — **append-only ledger**, unique per (delivery, attempt): outcome enum (sent | retry | failed | invalid), `error_code`, `provider_reason`, `provider_status`, `provider_message_id`, `request` JSONB (exact provider payload), `response` JSONB (status + first 4KB), `latency_ms`, `next_attempt_at`, `started_at`/`finished_at`. Never updated, never deleted.

### Engine (E1–E6, see [engine.md](engine.md))

Postgres keeps only definitions and control-plane facts: `segment` + `segment_version` (E3: the tenant-scoped definition with its slug, name, description and `current_version_id`; one immutable version row per expression change, `(segment_id, version)` unique, so a message pins the exact expression it was sent with; membership is never stored, it is a query over the stream, [api/segments.md](api/segments.md)), `campaign` + `campaign_run`, `workflow` + `workflow_version`, `webhook_endpoint` + `webhook_event` + `webhook_delivery` + `webhook_attempt` (E2: the endpoint with its secret, previous secret and failure streak; the immutable event object with its stored payload, unique per `(source, sourceId)`; one delivery per endpoint × event, unique; one row per attempt, [webhooks.md](webhooks.md)). Product events, subscriber lifecycle and run history are **not** Postgres tables.

**E1 (implemented).** The event stream has two homes, neither in Postgres. The **subscriber actor** (Durable Object SQLite, `apps/api/src/actor/subscriber.ts`): `events` (`sequence` autoincrement = the order, `id`, `idempotency_key` unique when set, name, source, occurred/received, `data` JSON text, `run_id`/`message_id`/`step`), `projections` (per name: count, last sequence, last at), `meta` (tenant, subscriber, external id, `flushed_sequence`); a rolling window of 10k rows. **Tinybird** (`packages/tinybird/src/datasources/`): `events` (ReplacingMergeTree on `(tenant_id, name, subscriber_id, timestamp, id)`, version `sequence`, monthly partitions, 13-month TTL), the materialized `events_by_subscriber` (sorted by subscriber and sequence: timelines) and `event_names_hourly` (AggregatingMergeTree per tenant × name × source × hour: the catalog and every volume chart; coarser tiers are sums over it), and the endpoints `event_catalog`, `event_volume`, `event_recent`, `subscriber_timeline` (the row readers use `FINAL`, so a replayed batch is never visible twice). `data` is a native JSON column for filtering (`data.total`), `data_raw` the serialized payload for reading back (the Events API stringifies array members in JSON columns); `workspace_id` rides along for hosted-level analytics. What cannot change without a rewrite is the raw table's sorting key and engine, which is why they are chosen for the two shapes every future feature reads: one name across subscribers, and one name for one subscriber; every other access path is a materialized re-sort that can be added and backfilled later.
