# Marketing site

`apps/marketing` → `@buzzkit/marketing`, the site at buzzkit.dev. Astro 7, fully static output, React islands wherever the page renders the product itself: the hero notification stacks, the dashboard preview, the feature and value cards, all composed from the real `@buzzkit/ui` components (Card, Table, Badge, Switch, PastelAvatar, the bklit charts) with fixed sample data, Tailwind v4 on the `@buzzkit/ui` tokens. Served from Cloudflare Workers static assets with a thin worker in front (`worker/index.ts`). Dev runs on port 5181; `bun run deploy` builds and deploys.

## Structure

```
src/lib/site.ts            Every external URL and the site meta, once
src/lib/content.ts         The homepage copy: hero, value props, features, deep dives (the two wide cards under the feature grid), FAQ
src/lib/pricing.ts         Plans, delivery rules, the matrix and the pricing FAQ; src/lib/estimate.ts is the calculator's math
src/lib/features/<slug>.ts One file per feature page, registered in lib/features/index.ts: menus, footer, llms.txt, sitemap and the
                           markdown twin all derive from it (`listFeatureGroups` is the grouped view the menu and footer share)
src/lib/compare/<slug>.ts  One file per comparison page (BuzzKit vs X), registered in lib/compare/index.ts, same derivations
src/lib/markdown/          The generated twins, one renderer per page kind (home, feature, comparison, pricing) over a shared
                           frontmatter contract and shared blocks
src/lib/llms/              The llms.txt bodies (home, features, compare, developers) and llms-full.txt (every twin in one file)
src/lib/structured-data.ts JSON-LD builders (page graph + FAQPage) · src/lib/responses.ts the endpoint Response shapes ·
                           src/lib/agent-index.ts the agent-skills index with its sha256 digest · src/lib/snippets.ts every code sample
src/lib/og/                The OG images: index.ts (the card list), visuals/ (one file per visual), primitives.ts
src/layouts/Site.astro     Meta, canonical, OG, JSON-LD (Organization + WebSite + SoftwareApplication + WebPage + BreadcrumbList)
src/components/            layout/ (Header island with its parts in header/, Footer + FooterColumn, Section, PageHero, ProseSection) ·
                           ui/ (Icon, Button, Badge, CodeBlock, Snippet, Logo) · sections/ (incl. Faq, DeepDive) · hero/ ·
                           platform/ (HeroPreview, DashboardPreview, the four screens) · features/ (vignettes/, FeatureVignette registry)
src/pages/                 index, pricing, developers, about, contact, privacy, 404, features/[slug] + [slug].md and compare/[slug] +
                           [slug].md generated from the registries, the twins and llms endpoints (thin: a lib renderer + lib/responses),
                           og/[...path].png, logo.png, apple-touch-icon.png (docs live at docs.buzzkit.dev; the worker redirects /docs there)
worker/                    index.ts (fetch) over routing.ts, negotiation.ts, headers.ts, session.ts: markdown negotiation + discovery
                           headers over the static assets
scripts/emit-agent-index.ts  Post-build: digests SKILL.md into .well-known/agent-skills/index.json through lib/agent-index.ts
test/                      Vitest (Node pool) mirroring src/ and worker/: worker helpers, twin and llms renderers, registry invariants,
                           reserved-slug coverage of every route, pricing math, the agent index digest; `bun run test` at the root runs it
```

Design follows [design.md](design.md): tokens only, Open Runde for everything except code blocks, which are mono (snippets are Shiki-highlighted at build time through a CSS-variables theme whose `--code-*` variables map to the status text tokens), superellipse corners, hairline shadows, the press pattern on buttons, checkmarks with the 4° rotation, springs at bounce 0. Product demos on the page are the real dashboard components rendered with sample data, cropped at the card edges the way Natural and Visitors crop theirs; never screenshots, never lookalike markup. The hero is a feature carousel (`HeroPreview`): a brand-tinted panel framing the real dashboard, rendered `inert` so it reads like a screenshot, and a floating black PillTabs pill at the panel's bottom edge that auto-advances every six seconds through Overview, Workflows (the real `WorkflowFlow` chart), Segments (the real `SegmentBuilder`) and Deliveries; a manual pick holds for twelve seconds and then the cycle continues. Screens swap instantly; the only motion is the sidebar's highlight sliding to the new page, through the same `useAnimatedIndicator` the dashboard sidebar uses. Every screen imports the dashboard's own components through `@buzzkit/web/components/*` and the deliveries chart keeps its axis while the card's bottom edge is cut off by the panel. The notification columns (`HeroStacks`) flank the hero title from `lg` up, anchored to the title's center with a gap that grows with the viewport (`clamp(1.5rem, 6vw - 2.5rem, 10rem)`), and never hold two rich cards (a Live Activity or an actions card) on the same side at once. Buttons come in one size; there is no large variant. The site is light only: the `.dark` class is never set, so the token file's dark values stay dormant.

Icons render through `src/components/ui/Icon.astro`, which reads the generated `@buzzkit/ui` icon paths. The generator scans `.astro` files too, so `name='IconX'` literals in this app are picked up like everywhere else.

The header collapses like CruiseSignal's: 16px of top padding that folds to 0 past 20px of scroll while a hairline fades in, always on a solid background, with the Features menu (grouped Send / Automate / Platform / SDKs, one-line blurbs; the same `FEATURE_GROUPS` order drives the footer) fed from the feature registry; the comparison pages are linked from the footer only. The nav highlight pill presses with the button's fixed inset. `apps/marketing/CLAUDE.md` carries the rules an agent must follow in this app.

## The agent surface

The site is built to be read by agents as much as by people. What it serves, and what must stay true:

- **`/llms.txt`** (`src/lib/llms/home.ts`, served by `src/pages/llms.txt.ts`): what BuzzKit is, a "when to use BuzzKit" section, and links. Every link in it must resolve; when a page moves, fix it here in the same change (`test/lib/llms/*.test.ts` checks every buzzkit.dev link against `public/` and the generated paths).
- **Markdown twins**: `/index.md`, `/pricing.md`, `/features/*.md` and `/compare/*.md` are generated at build by `src/lib/markdown/` from the same data the pages render; `/why-buzzkit.md`, `/developers.md`, `/about.md`, `/contact.md`, `/privacy.md` and `/auth.md` are hand-kept files in `public/`. `/llms-full.txt` is every twin in one file. A copy change on a page changes its twin in the same commit. Twins open with `---` frontmatter (title, description, canonical, last-updated) and a single `#` heading; every code fence closed (`test/lib/markdown/contract.ts` asserts this for every generated twin).
- **The API for agents**: `/openapi.json` is emitted from the API contract by `apps/api/scripts/openapi/emit.ts` (summaries, camelCase operation ids, the `bearerAuth` scheme, servers) and re-emitted at the start of every marketing build; `/.well-known/api-catalog` (RFC 9727 linkset, served as `application/linkset+json`) and `/auth.md` (the WorkOS auth.md shape: discover, pick a method, register, claim, exchange, use, errors, revocation, all about API keys because BuzzKit has no OAuth) describe how to reach and authenticate against it. `/docs` and `/api` redirect to docs.buzzkit.dev; `/developers` is the developer hub page (quickstart, keys, reference, SDKs, sandbox, agent files). `?mode=agent` on any page serves llms.txt; `/developers/llms.txt`, `/features/llms.txt` and `/compare/llms.txt` are the section indexes.
- **Signed-in hint**: the dashboard's session cookie lives on the shared cookie domain, so the worker sees it on buzzkit.dev. When it is present the worker stamps `data-signed-in` on `<html>` (HTMLRewriter) and the header's account button reads "Dashboard" instead of "Get Started" — both links are in the HTML and CSS hides the wrong one, so the right label is correct at first paint with no hydration flash; nothing about the session is read, only that a cookie of that name exists. The Astro dev server has no worker, so it always shows "Get started".
- **Content negotiation**: the worker serves the `.md` twin for `Accept: text/markdown` and for AI crawler user agents, with `Vary: Accept`, and stamps `Link:` discovery headers (sitemap, llms.txt, `rel="ard"`, api-catalog, `rel="service-desc"` for the OpenAPI document) on every response. Unknown paths return a real 404: `dist/404.html` for browsers (an `Accept` that names `text/html`), `public/404.md` with links to llms.txt, the sitemap and the docs for everything else.
- **`/.well-known/`**: `ard.json` (the Agentic Resource Discovery catalog: `specVersion`, `entries[]` with `urn:air:buzzkit.dev:*` identifiers, media types, representative queries and capabilities; the worker also serves it at the legacy `ai-catalog.json` path), `api-catalog` (RFC 9727), `security.txt` (RFC 9116, expires yearly), `agent-skills/index.json` (generated post-build with the SKILL.md sha256 digest) and `agent-skills/buzzkit/SKILL.md`, the installable integration skill. The skill's claims come from `docs/api/*`; when the API changes, the skill follows.
- **`robots.txt`**: explicit allows for the AI assistant and search crawlers, a `Content-Signal: search=yes, ai-input=yes, ai-train=yes` line (BuzzKit wants to be in the models' knowledge), plus the sitemap. Never a blanket disallow that catches user-triggered agents (ChatGPT-User, Claude-User, Perplexity-User).
- **Structured data**: Organization (with `contactPoint` and the PNG logo), WebSite, SoftwareApplication and a WebPage node on every page, a BreadcrumbList on every page but the homepage, FAQPage wherever an accordion renders (home, features, comparisons, pricing) built from the same arrays. The sitemap's `lastmod` is the last git commit of the page's source file (registry entry, `content.ts`, `pricing.ts` or the `.astro` page); an uncommitted page has none.

**The scanners' checks live in the repo as tests.** `apps/marketing/test/dist/*.test.ts` audits the built `dist/` the way Is Agentic (`npx is-agentic <domain> --json`, essential/recommended/bonus) and Ora (`npx ax audit <url> --json`, the check catalog at `ora.ai/api/checks`) do — per page: metadata, canonical, OG image on disk, JSON-LD graph (Organization with contactPoint, WebSite, SoftwareApplication, WebPage, BreadcrumbList, FAQPage exactly where an accordion renders), one `h1`, server-rendered text, named controls, described images, labelled inputs, every internal link and asset resolving, the markdown alternate link; every twin against the frontmatter contract; `llms.txt` and the section indexes; `llms-full.txt` bundling every twin; `robots.txt` allows and `Content-Signal`; the sitemap listing exactly the pages; `ard.json`, the RFC 9727 `api-catalog`, `security.txt` unexpired, the agent-skills index digest against the served SKILL.md; `openapi.json`, `auth.md`'s sections, the trust anchors and `404.md`. `test/worker/contract.test.ts` drives the real worker over `dist/` through a fake `ASSETS` binding and pins the negotiation and header matrix. `bun run test` builds first so the suites always see the real artifacts (`bun run test:only` skips the build). The live scanners stay the source of truth; the official Is Agentic agent skill is installed at `.claude/skills/is-agentic/SKILL.md` (digest-verified against `is-agentic.com/.well-known/agent-skills/index.json`) so an agent can fetch a report and work the issues by tier. When a scanner adds or changes a check, add its assertion to the matching suite in the same change as the fix, so the score can never regress silently. Not testable offline (live infrastructure or third parties): brand and category search discoverability, Wikipedia/Wikidata presence, npm/skills.sh/MCP registry listings, bot-detection and crawler reachability, redirect hygiene of the live host, the `api`-scoped checks against api.buzzkit.dev, and everything MCP/OAuth/payments the site deliberately does not pursue.

Audit against this surface with `npx is-agentic <domain> --json` (the tiered view: essential, recommended, bonus) and `npx ax audit <url> --json` (Ora's full 127-check report) and work the essential failures first. Reports cache for six hours; a query string on the target forces a fresh scan. Before the domain is live, `bunx wrangler dev --port 8799` behind an `ngrok http 8799` tunnel gives the scanners something to hit; links inside llms.txt and the sitemap still point at buzzkit.dev, so those two checks read as failures until the real domain serves. Deliberately not pursued: MCP servers, OAuth and RFC 9728 metadata, NLWeb, WebMCP, agent payments, a `?mode=agent` view. Open: a Terms page (trust anchors) and a postal address in the Organization schema.

## The OG images

One 1200×630 card per page, rendered at build by `src/lib/og/` with satori and resvg on the subset Open Runde TTFs in `src/assets/fonts/`: white ground with the hero's brand glow, logo and wordmark top left, the page's title in `fg-4` with its gray continuation under it, `buzzkit.dev` and the page's kicker (feature name, Compare, Pricing, Open source) along the bottom, and a page-specific visual top right, each a faithful redraw of the site's own component at 1.3× (Card, Table, Badge, Switch, PastelAvatar, the notification artifacts, the flow nodes): notification banners by default, on comparisons and on pricing, the actions artifact for the iOS SDK, the Live Activity lifecycle, the workflow nodes, the segment chips over its members, the preferences sheet, the delivery ledger, the schedule table, the sources table, the tenants table and a workspace key card on developers. Titles are balanced like `text-wrap: balance` by measuring words with the real font. The card list is the page list: the homepage, every feature and comparison, pricing, about, contact and privacy; `Site.astro` takes `image` and each page passes `/og/<path>.png`. `logo.png` (512) and `apple-touch-icon.png` (180) are rasterized from `favicon.svg` the same way.

## Routing on buzzkit.dev

The marketing site and the dashboard share one hostname. The marketing worker claims only its own paths through explicit Worker routes (`apps/marketing/wrangler.jsonc`): the root, `/index.md`, `/features/*`, `/compare/*`, `/pricing`, `/about`, `/contact`, `/privacy`, `/docs`, `/llms.txt`, `/robots.txt`, `/sitemap*`, `/.well-known/*`, `/_astro/*`, `/flags/*`, the logo files, `/404` and `/internal/*`. The dashboard worker takes `buzzkit.dev/*`, and Cloudflare's route precedence sends a request to the more specific pattern, so `buzzkit.dev/gymly` reaches the dashboard while `buzzkit.dev/pricing` reaches the site. Every marketing path is a reserved workspace slug in the API (`apps/api/src/utils/reservedSlugs.ts`), so a workspace can never shadow a page; `test/lib/reserved-slugs.test.ts` reads the route list from `wrangler.jsonc` and fails when a segment is missing from that set. The site links the dashboard as `buzzkit.dev/dashboard` (its entry, which redirects to the last workspace) and sign-up as `buzzkit.dev/signup`; the product docs live at `docs.buzzkit.dev`. Because the domain is shared, the session cookie the worker reads for the signed-in header hint is first-party.
